1. The sensor captures a process start identity and opens the actor executable. Windows uses a process handle/start FILETIME and an image file handle. Linux uses a PIDFD, boot ID/start ticks and `/proc/<pid>/exe`. The original audit subject is kept separately from a later process-owner observation.
2. The original observation, including capture state, is durably spooled before expensive enrichment. The sensor worker has at most 32 outstanding image leases. Overflow retains the observation and records that hashing/preservation were unavailable.
3. A background worker hashes the **actor executable**, verifies Windows signatures and applies the preservation policy. It never hashes or preserves the target file. Existing, explicitly configured canary integrity checks remain independent.
4. Completion is a new immutable event with `RelatedEventId`, the original process instance, collector epoch/sequence and monotonic ticks. An interrupted worker leaves a visible pending original; it does not manufacture completion after restart. Automatic response events carry the original process/event linkage too.
5. Management delivery requires an explicit `ForensicsVersion: 1` capability and receipt. A published forensic policy also requires a versioned policy receipt; old sensors remain pending. The server stores the entire envelope, returns it through Event History and forwards structured JSON to SIEM. Whitelist decisions are independently replayed by the server; linked forensic completions of log-only events are also excluded from alert forwarding.

## Identity, cache and preservation

- PID is never a durable identity. Process correlation is SHA-256 of sensor ID, PID and platform start key. Parent start/correlation is populated only when observable and not newer than the child. Collector sequence is scoped to a random service epoch; source audit sequence is retained separately. Per-process counters stop being allocated when their bounded registry is full rather than restarting after eviction.
- The actor hash/signature cache uses stable file identity, size and change marker. Windows uses volume + 128-bit file ID and basic file times; Linux uses device/inode plus nanosecond ctime/mtime. Identity is checked before and after hashing and on cache hits. Cache capacity is configurable and trust verification expires after five minutes, because certificate policy can change.
- Windows verification uses WinVerifyTrust against the opened file, then installed catalog lookup for unsigned embedded images. Evidence includes native trust/signer error codes, signer certificate details, countersignature results and PE version fields. Revocation is **cache-only**, avoiding an endpoint I/O dependency on external certificate services. A successful result is not a fresh online revocation check or a safety verdict.
- Preservation writes a unique `.bin` artifact and JSON manifest below the sensor's `evidence/actors` directory. Windows grants the service identity, SYSTEM and administrators access; Linux directories are 0700 and files 0600. Files are created with exclusive create semantics and are never executed or silently overwritten. The preserved artifact is independently SHA-256 hashed and compared with the event hash. The manifest includes original identity, times, process and source-event linkage; its hash is included in telemetry.
- Default sensor limits: preserve alert-level actors, maximum actor 256 MiB, evidence store 1024 MiB, cache 256 entries. Lowering a limit does not delete evidence. Quota, permission, image disappearance, modification and hash mismatch failures are recorded. Windows 0.6.11/Linux 0.9.17 automatically queue newly preserved executables for authenticated upload. They retain local evidence on receipt and do not backfill historical artifacts.

## Evidence boundaries

### Whitelist comparison versus forensic collection

Reviewed 2026-09-25 against the current deployed source/package version. The Trust rules page supports manual creation without an event. Its new process rules select `event-path` by default: an absolute executable path is required, but matching that rule does not authenticate the executable bytes. The optional Windows path + SHA-256 mode uses ProcessControls' fresh process/start-time and locked-image checks; a missing or different hash cannot satisfy it. The current Linux whitelist adapter intentionally supplies only audit-time account/path identity and does not consume the later forensic SHA-256. Windows signature, publisher and PE metadata are stored as forensic evidence; the live Windows whitelist actor does not populate its signature/signer/publisher fields, so predicates requiring those fields remain unmatched. None of these collectors verifies injected process memory or treats a valid signature as proof of safety.

Forensic preservation writes an actor `.bin` and JSON manifest locally and delivers their hashes, status, original path and event linkage in structured server events. The current builds also include the transfer endpoints and worker below. Local preservation success must never be described as central possession without a committed server receipt. Collection still depends on configured thresholds/limits and the observable process/image; failure states retain the event and available evidence.

### Central transfer contract

`EvidenceUploadVersion: 1` advertises support. Sensor-authenticated POST `agent/evidence/start`, POST `{id}/status`, PUT `{id}/chunks/{offset}`, and POST `{id}/finish` live under `/api/v1/`. The original/completion events must already belong to that authenticated sensor; exact manifests and actor hashes bind transfer identity. Chunks are capped at 256 KiB. Durable queue attempts are bounded and rotated, with local originals retained. Old servers leave delivery pending rather than discarding artifacts.

Server 0.6.14 separates artifact endpoint traffic from the reporting/management request budget. Each pool allows 600 requests/minute, with no queued requests at the limiter. Actor downloads share the artifact pool. Saturated uploads therefore cannot consume the heartbeat/event/policy request allowance. Clients retain interrupted uploads and resume later; a partially received artifact is not successful central preservation.

The private server store is `<data-dir>/actor-evidence`, outside static content. Default server limits are 256 MiB/artifact, 1 GiB/sensor, and 10 GiB total reservations, configured by `Forensics:MaximumUploadMiB`, `PerSensorStoreMiB`, and `TotalStoreMiB`; at most 32 receiving transfers are allowed per sensor. An abandoned reservation remains charged; automatic expiry/deletion is not implemented. SQLite creates the additive table; SQL Server requires migration component `actor-evidence` version 1, whose native rehearsal remains pending.

Independent artifact/manifest verification and file finalization precede a database transaction containing the receipt, audit entry, and linked `Evidence transfer` event. Its optional `Forensics.Transfer` includes evidence/completion/receipt IDs, hashes, size and receipt time; it uses server ordering, not invented sensor sequence numbers. Sensors cannot submit this server-owned event through ordinary ingest. Existing structured SIEM output includes the transfer evidence. Windows uses protected file ACLs with execute denial; Linux uses 0700/0600 and directory sync. Neither is a remote attestation or proof against a compromised administrator.

Administrator/Operator console routes under `/api/v1/console/actor-evidence/{sensor}/{id}` expose receipt and audited attachment downloads (`artifact`/`manifest`). Download revalidates the digest. The UI offers links only after a received receipt and distinguishes missing or partial transfer. It does not execute, extract or preview artifacts. A receipt confirms verified bytes received at its recorded time; filesystem/DB recovery is tested at process-crash boundaries, not every possible storage power failure.

### Linux hash authorization boundary

A pidfd and process start ticks identify a lifetime, not an exec generation. `/proc/PID/exe` is a later snapshot. Native QA reproduced two different executable hashes with the same PID/start ticks while holding a pidfd. Path/start/descriptor consistency checks remain useful forensic enrichment but do not establish all event-time content bindings, including same-path replacement/re-exec races. Consequently the live Linux whitelist adapter still omits SHA-256, and unknown binding cannot suppress an alert. The future provider must bind operation-time executable identity, exec generation and content, account for collector loss/restart, and revalidate policy before applying a hash rule. fs-verity measurements must be separately typed rather than substituted for whole-file SHA-256.

### Windows kernel evidence boundary

Protocol 4 captures CREATE `AccessState.SubjectSecurityContext`, the provided request thread's effective token and the requestor's primary token as three separate observations. A non-impersonating thread uses its creating process's primary token; that process can differ from Filter Manager's attached requestor process. Thread owner PID and requestor PID are separate. Token fields carry captured masks, raw status codes and an explicit non-atomic multiquery status. A missing request thread does not erase available CREATE authorization. Native scenarios validate token SID/ID/logon/type/session/integrity/elevation and transitions between open and later read. Requested rights, failed NTSTATUS, name provenance, IRQL and ordering are retained. Journal-before-ACK, immutable originals and version-aware management receipts protect delivery through the existing pipeline. The deployed audit collector still has no actor TID and keeps thread-token fields unavailable. Null-thread/high-IRQL paths, SMB, other filesystems, full mapped/paging coverage, older Windows native qualification and production signing/altitude remain qualification work. [Full implementation and release gates](WINDOWS-KERNEL-CAPTURE.md).

### Linux service permissions

The deployed service runs as `rfclient`. Linux checks access to another user's `/proc/PID/exe` using ptrace credentials. An audit event can contain the correct user/PID while this later image capture is denied. The Plex pilot exposed this distinction: native root-run fixture checks passed, but the unprivileged installed service could not capture the root-owned Python reader.

`packaging/linux-client/forensics/30-actor-evidence.conf` is a prepared, separately authorized deployment setting adding `CAP_SYS_PTRACE` and `CAP_DAC_READ_SEARCH`. It retains `User=rfclient`, `NoNewPrivileges`, and existing filesystem restrictions. These capabilities broaden cross-user process inspection and protected-file reading; they are not implied to be harmless. Evidence remains owned by the service account, directories 0700 and files 0600. Mandatory access controls and process exit can still prevent collection.

**Approval and runtime acceptance:** automatic approval review initially rejected applying these capabilities without exact user approval. The user subsequently approved the two capabilities for Plex and the other 25 Linux sensors after pilot success. All **26/26 installed-service cross-user reads, actor copies and live server comparisons passed**, including exact process start keys, device/inode and independent binary/manifest hashes. The 39 root-run Linux native checks remain separate from these installed-service tests. The binary archive was retained unchanged; the approved service drop-in has its own SHA-256 receipt and remains in the persistent systemd configuration directory.

The existing production collectors cannot guarantee actor handles for **every** short-lived process, actor thread tokens on Windows, process-start events before sensor startup, or complete pre/post I/O measurements. The kernel prototypes are not silently substituted or shipped as production collectors. These gaps are explicit evidence states, not discarded events or invented values. SIEM correlation must distinguish observation time, capture time, completion time, source order and collector order. A pending original with no linked completion needs investigation.
