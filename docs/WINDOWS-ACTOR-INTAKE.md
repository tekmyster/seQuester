## Implemented boundary

The existing protocol-4 operation record is unchanged. It retains CREATE authorization, the actual request thread's effective/impersonation token and the requestor process's primary token separately, including SID, token/authentication IDs, session, integrity, elevation and query statuses. PID is correlated with process creation time. Missing evidence is explicit and does not discard the operation.

An additive `ActorAcquisitionEvidence` version-1 record links an operation to a provider UUID/status, event instance/sequence, nonreused process generation and candidate ID, PID/start, execute-access qualification and byte-copy interval. The original actor path and diagnostic file index remain separate from the private snapshot's descriptor identity. Source volume identity is not yet collected; a 64-bit source index is not presented as a globally stable identity. Captured bytes are a backing-file interval read, not an atomic original-file snapshot or proof of executed memory contents.

Private executable snapshots are flushed, reopened and independently SHA-256 verified. The existing forensic collector checks signature/version information and preserves the actor executable from this held snapshot; the existing evidence queue uploads the executable and manifest. No target-file hashing or copying was added. Failures retain raw operation/token evidence. Snapshot recovery failure retains validated historical metadata, marks recovery failed, and cannot fall back to a later PID/path image.

The snapshot store keeps immutable manifests, unique object IDs, restrictive permissions and a 512 MiB quota. It currently lacks retention/garbage collection. Proactive process acquisitions now have a framed PREPARE/COMMIT journal; the legacy event-bound acquisition path and raw operation records do not yet have that journal format. A flushed file plus an atomic manifest rename is not a claim of multi-file transactional crash recovery. Full crash-cut qualification remains pending.

## Whitelist integrity

The Windows agent can use `windows-operation-bound-snapshot-v1` as a process identity basis. The hash is accepted only from an unchanged held snapshot whose event, provider, process generation, PID/start and observed path match the current observation. Server classification independently verifies acquisition linkage, SHA-256, timestamps and the original operation-time user claim. An exact path/hash rule cannot be satisfied by changing the name of a different binary. A signature or PE metadata is never treated as a safety verdict.

Existing explicitly selected event-path rules retain their weaker documented semantics. Missing acquisition evidence or contradictory SHA-256 cannot suppress an alert under a snapshot/hash claim. Rules still limit suppression to selected actions and retain the event as log-only. Linux hash-based whitelist integration remains outstanding.

## Native ownership and retrieval

Diagnostic bounds remain explicit: 64 candidate metadata entries, 256 process registry entries, 8 MiB per image, 32 MiB total byte credit and R11 uses 32 concurrent qualification callbacks and a separate 16-slot full-copy cap. The earlier R8/R10 boundary used one shared 16-callback cap. Additive command 24 reports both active/peak/refusal counters; legacy health still reports the outer callback bound.
