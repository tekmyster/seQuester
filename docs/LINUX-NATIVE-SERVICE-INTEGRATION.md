# Installed Linux native source integration

Status: implementation design, October 03, 2026. The native source is qualified in the isolated VMware system and has real server/UI acceptance. This document does not enable an installed service or assert support for other kernels.

## Existing components and boundaries

The installed `RansomFree.LinuxAgent` runs as `rfclient`, without capabilities. `LinuxWorker` owns its management connection, deployment and monitoring, trust cache, event spool, response handles and local syslog queue. The separate root Audit collector produces a protected inbox. Audit remains necessary for operation coverage that the native pre-open hook does not provide.

`LinuxControlledSourceRuntime` currently has a qualification-only entry point. It owns the loader child and pidfd, exact retained maps and controller, source journal, raw reserve and native worker. Its target identities are prepared independently, then checked against the loader and frozen map. `ForensicPipeline`, `LinuxForensicJournal`, `EventSpool` and `EvidenceUploadWorker` already supply retained originals/completions and actor artifact transfer. A second process must not mutate the existing installed worker's spool, upload queue or cache files.

The accepted native package is limited to Linux x64, kernel `6.12.94+deb13-amd64`, the recorded BTF/loader/object/module hashes, local ext4 regular actor images up to 4 MiB, and 1-32 frozen target identities. There are four bounded native leases. Source observations mean `OPEN_REQUEST` and `NOT_OBSERVED` outcome. Earlier DAC denials and arbitrary write/rename/delete operations are not covered by this source.

## Implementation choice after R111 review

Use a separate opt-in privileged companion while retaining the ordinary worker's current service identity and sandbox. Publish a bounded root-owned immutable bridge inbox for the ordinary worker. It transports exact committed events and actor artifacts without running policy or forensic collection again. Keep the ordinary worker as the only network/upload/readiness reporter. The initial direct-sender proposal is superseded by the R111 review.

The companion must not overwrite ordinary sensor heartbeat/version/protection status. Both event streams retain the same enrolled sensor identity and distinct event IDs. Root-private state holds native journals, raw reserves and actor copies. Exports use a dedicated group containing only the sensor service account, not the UI group. Root-owned installation configuration binds the server origin, sensor ID, policy-verification public key, approved targets and exact qualified package. Unprivileged writable data cannot choose a root executable/module, expected artifact hash, server or arbitrary capture target. An acknowledgement releases only an export duplicate after durable import; it never authorizes native calls or deletion of root raw evidence.

The root policy channel will use a server-signed envelope relayed by the ordinary worker. The privileged process pins the verification key during installation and creates a fresh challenge; the envelope binds that challenge, exact sensor/server, trust assignment and general forensic/deployment assignment from one consistent server snapshot. Verification precedes root policy acceptance. A digest alone or the ordinary worker's mutable cache cannot authorize suppression. Expiry, monotonic challenge deadline, exact schema, consumed challenges and durable revision floors must prevent replay. This additional signing concerns policy authenticity, independently of operating-system driver signing.

No activation command is added until these boundaries have been implemented and qualified. The normal agent cannot use a health file as authority to suppress an event. Only the live native owner can form the bound, immutable event decision.

## Start, update and stop invariants

1. Validate installation and source prerequisites before loading/attaching. A previous unresolved native owner or close blocks a new session. Journal records do not recreate native capabilities.
2. Validate targets independently and freeze their device/inode set for one source session. Replaced, deleted or newly deployed targets require stop/drain/revalidation. Do not silently edit a live watch map.
3. Policy refresh must retain exact assignment/group/revision/digest. Committed decisions never change. If a changed forensic policy or target/group assignment invalidates the running configuration, stop new admission and drain before creating the next session.
4. Source loss, child failure, disk pressure or spool backpressure must become visible. Keep original raw/prepared evidence. A stop cannot be reported complete before the actual controller return and required durable receipts.
5. An interrupted or unreturned native operation blocks automatic unload/restart. Service-manager hard-kill timeouts must not fabricate successful cleanup. Capture diagnostics and use an explicit recovery state.
6. Stopped-source replay never creates new whitelist eligibility. Any incomplete operation remains recorded with explicit unavailable/unknown evidence.

## Qualification cases

- Supported installation starts; wrong kernel/BTF/module/loader/object, unsafe ownership/links, changed credential/server/sensor, unsupported filesystem and too many targets refuse startup.
- Existing Audit, enrollment, heartbeat, canary deployment and event delivery continue normally with companion disabled or unavailable.
- Actual ordinary-user actor opens reach the same server sensor with exact user/process/PID, process instance, SHA-256, original decision and verified actor copies where required.
- Policy/group/target changes, source loss and old-process health receipts cannot create stale readiness or a new suppression decision.
- Current, stale, regressing, replayed and different-boot/process/session health samples; monotonic progression and clock jumps.
- Spool capacity/disk errors, process crash before/after commit, interrupted native calls, restart refusal, eventual drain and exact returned cleanup.
- Service packaging/start/stop/restart on the owned VMware Linux system, then final qualification of each additional supported kernel before rollout.
