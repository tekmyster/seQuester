## Distinct identities

Protocol 4 keeps three independent snapshots:

1. **CREATE authorization:** `AccessState.SubjectSecurityContext`, including when the request-thread pointer is absent.
2. **Request-thread effective context:** a referenced impersonation token from the actual `FLT_CALLBACK_DATA.Thread`, or the primary token of that thread's creating process when it is not impersonating.
3. **Requestor-process primary context:** the process returned by Filter Manager. Windows can attach a thread to a process different from the one that created it. Thread owner PID and requestor PID are separate fields; they are not assumed equal.

Each snapshot records SID, token ID, authentication/logon ID, modification ID, token type, impersonation level where applicable, session, integrity RID, elevation, captured-field mask and native query status codes. Thread ID, impersonation state, copy-on-open and effective-only flags are retained. These are forensic metadata, not transferable token handles or credentials. This does not serialize every possible token field, group, privilege or claim.

A referenced token prevents replacement of the token object; it does not make multiple queries atomic. A changed modification marker invalidates the statistics result. Every snapshot explicitly states `separate-field-queries; modification-checked; not-atomic`. Missing data is null with native status, never copied from a different identity to fill a gap.
