## Included

- Self-contained .NET service, one-time HTTPS enrollment, validated server certificates, revocable endpoint bearer stored in service-private state, cached group policy and deployment receipts.
- Explicit administrator-approved folder aliases; immutable deployment identity; exclusive, no-symlink canary creation; original files and incomplete deployment intents preserved. Removed policy rows retain files and monitoring. No automatic scattering into OS/user folders.
- DOCX, XLSX, PDF, TXT, CSV, RTF, HTML, SVG, JSON, XML and Markdown generation. Managed callback association for DOCX/XLSX/PDF/HTML/SVG. Callback activation depends on the reader, remote-content permission and receiver reachability. This does not implement every Canarytokens-site mechanism as an endpoint file type.
- inotify opens/access/changes/deletes/renames/metadata monitoring; startup bounded content verification; periodic non-reading metadata checks. Encryption is a possible explanation for writes, not a proven classification. A content read is “copy possible,” never proof of a copy.
- Optional fanotify PIDFD events for read/open/write attribution. UID/effective UID and executable/hash are best effort while the process lives. Delete/metadata events currently remain unattributed. No fabricated identity for inotify events.
- Default-off administrator/local-approved manual and automatic process response, stable event-bound PIDFD, five-minute local evidence window, exact path + SHA-256 allowlist with folder/expiry, protected root/capability processes, automatic rate limiting, persisted intent/results. SIGTERM is followed by a two-second PIDFD exit check; only a confirmed exit reports success, otherwise indeterminate. Process trees are not stopped. The allowlist suppresses response and tray popups, not management evidence collection. Automatic delete/permission response is rejected on Linux. Automatic outcomes also enter the management evidence stream.
- Transactional SQLite management queue, bounded policy-configurable capacity, FIFO retry after connectivity returns, exact receipt acknowledgement and EventId deduplication. Defaults: 10,000 events / 128 MiB; a full queue preserves old evidence and reports new enqueue failure. The in-memory native event channel is bounded at 4,096; overflow is explicitly reported, not lossless capture.
- Independently administrator-configurable direct syslog (UDP/TCP/TLS, RFC3164/5424), separate persisted 1,000-event outbox; all events still take the management path. Existing queued syslog destinations are retained. Pausing syslog preserves queued items. UDP/TCP send does not prove Wazuh persistence. Server-side email/syslog remains centrally configured.
- Compiled C#/.NET 10 Avalonia desktop window and tray, managed alert popups, health/connectivity/stale-state presentation, recent events, no private credential access or control endpoint. Explicit approved desktop group only. Headless installations need no desktop runtime libraries.
- systemd, stopped first installation, local configuration generator, password-checked enrollment/maintenance, preserve-data unregister operation and documented version rollback.

## Target requirements

Candidate targets: x86-64 and ARM64 **glibc** Linux with systemd; Ubuntu 22.04+/Debian 12+/RHEL 9-class systems. These are intended targets, not a certified compatibility matrix. Install .NET native prerequisites (libc, libstdc++, ICU, OpenSSL, zlib, CA certificates) through the distribution. Alpine/musl, containers, network filesystems and kernel/distro combinations are not accepted targets yet.

inotify mode requires normal directory search/file access permissions. fanotify requires a kernel supporting FAN_REPORT_PIDFD (upstream 5.15+ or applicable backport) and CAP_SYS_ADMIN; the .NET configuration command also grants CAP_DAC_READ_SEARCH/CAP_SYS_PTRACE for evidence access, and CAP_KILL only when response is locally enabled. These are broad privileges, especially CAP_SYS_ADMIN. **Do not select fanotify merely to clear a health warning.** No kernel capability, audit rule, sysctl, firewall rule or privilege is changed by building this package. Unsupported fanotify fails explicitly instead of silently claiming inotify has process identity.

Monitoring is notification-only, not a ransomware-blocking filesystem lock. Events can coalesce/overflow; mmap, remote filesystem operations, renames/hardlinks and very short-lived processes impose attribution/coverage limits. Periodic metadata checks do not detect an attacker restoring size/mtime; startup hashes are content verification, not continuous hash proof. Local root can bypass the application and maintenance password. No anti-root/uninstall-proof claim is made.

## First installation (operator action; not executed by packaging)

1. Verify the archive SHA-256 against a separately trusted build record. Extract into a root-controlled staging directory and run `sha256sum --check --strict SHA256SUMS`. Checksums detect changes; unsigned files do not authenticate a publisher.
2. Copy client.json.example to a root-owned file, mode 0600. Set `Server` to the actual HTTPS origin, and `Folders` to explicit aliases such as `{"finance":"/srv/lab-decoys/finance"}`. Create/approve those folders separately. The installer never changes existing folder permissions. Give the service identity only the necessary directory search/create and file access rights after installation. Do not put credentials or enrollment codes in JSON or process arguments.
3. Run `sudo bash install.sh /absolute/path/client.json`. The installer refuses an existing installation/account/config/state and preserves partial results for review. It creates `rfclient` and `rfclient-ui`, root-owned versioned binaries under `/opt/ransomfree-client`, private state mode 0700, config mode 0640 and a systemd unit. It **does not enable/start/enroll**. Review the generated systemd capability/ReadWritePaths drop-in before starting.
4. From the installed current directory run `sudo bash setup.sh`. Supply a maintenance password (12–256 characters), then that password and a one-time server enrollment code through the terminal/standard input. Public CA/private CA trust must already be installed by your administrator. No skip-TLS option exists.
5. Assign this endpoint to a compatible management group; disable unsupported automatic delete/permission triggers. Then explicitly run `sudo systemctl enable --now ransomfree-client.service` when ready to deploy canaries from that policy.
6. Inspect `journalctl -u ransomfree-client.service`, server endpoint health/policy receipt and read-only status. Run `runuser -u rfclient -- /opt/ransomfree-client/current/app/RansomFree.LinuxAgent --diagnose` only when an outbound HTTPS connectivity probe is intended. DNS/TLS/HTTP failures are reported; ports are not opened automatically.

No inbound client port is required. Allow outbound management HTTPS and optional configured syslog destinations only. Passive callback documents contact the callback receiver from whichever reader opens them, not necessarily the endpoint.

## CLI and .NET implementation

The separate `app/RansomFree.LinuxAgent` supports `--run`, `--enroll`, `--status`, `--diagnose`, `--set-password`, `--verify-maintenance`, `--validate-config` and `--version`. The service and CLI do not load Avalonia or require a graphical login. The desktop is read-only; settings and provisioning remain administrator CLI/management-console operations.

Configuration validation and systemd drop-in generation now run inside the .NET agent through root-only `--stage-config INPUT_JSON PRIVATE_DIRECTORY`. It rejects duplicate/unknown JSON, invalid paths/permissions and unsupported response modes; staging never starts a service. `--same-server OLD_JSON NEW_JSON` guards maintenance origin changes; `--package-runtime MANIFEST_JSON` guards architecture selection. Standard shell wrappers invoke OS service/account tools; these are bootstrap scripts, not a Python application runtime. Original 0.7 sources/packages are retained separately, excluded from new packages.

Status contains file paths/process/user evidence; membership grants access to that sensitive read-only view. State contains a bearer in mode-0600 files inside mode-0700 directories (not encrypted at rest by this client). Use OS disk encryption and protect stopped backups. The tray never reads canary contents or private state. Quitting it does not stop monitoring.

## Maintenance and recovery

Use `sudo bash /opt/ransomfree-client/current/maintenance.sh stop|disable|password|configure|uninstall`, adding an absolute new JSON path for configure. The wrapper verifies the maintenance password before service/config changes, leaves the service stopped, retains previous config/drop-ins and refuses server-origin migration. Uninstall unregisters the unit but keeps binaries, state, credentials, accounts, config and canaries; deliberate secret disposal/file retirement is a separate administrator decision. OS root can bypass this wrapper. There is no claim that a local password blocks systemctl, root or package-manager actions.

Before an upgrade: stop with the wrapper and make a **stopped** protected backup of the complete state/config/unit/drop-in plus the versioned binaries. Verify the new immutable package; place it in a new root-owned release directory, review schema/release notes, update only the root-owned current symlink and start explicitly. Do not merge a live SQLite DB with unrelated WAL/SHM files. Rollback must restore a mutually compatible stopped state/config/binary set. Automated updater, DEB/RPM repository, fleet enrollment broker and native upgrade acceptance remain backlog; this archive installer does not pretend to provide them.

Pending deployment intents block automatic recovery instead of overwriting a possibly changed file. Retain canaries.json and affected files, investigate and restore from a coherent backup or perform an explicit reviewed migration. Revocation never automatically discards queued evidence. Response journal limit is 2,000 entries; dated acknowledged receipts age out after 30 days, while undated/unacknowledged entries are preserved. Full journals reject new signals. Expired commands never regain execution eligibility. Maintain protected backups/central response evidence before production.
